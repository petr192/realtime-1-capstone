# Проект. Соберите свой realtime-пайплайн

Суть: собрать в одном репозитории работающий путь от изменения в исходной
базе до ответа API. В лабах мы делали отдельные части; в проекте надо
соединить их и показать, что изменение в источнике доходит до результата.

Для проекта нужен работающий end-to-end пайплайн и инструкция, по которой
его можно запустить и проверить. Обязательный минимум описан ниже;
в разделе «Идеи для развития» собраны необязательные эксперименты.

Можно продолжить историю с заказами и использовать свои решения из лаб. Ещё
лучше, если у вас есть своя задача, на которой хочется попробовать материал
курса: продуктовая аналитика, платежи, склад, поездки, что-нибудь из работы.
Опишите, кто пользуется результатом и какое решение принимает по этим
данным. Если задача заметно отличается от предложенной ниже, обсудите её в
чате до того, как потратите на неё выходные.

## Что собираем

Знакомый стек вполне подойдёт:

```text
PostgreSQL -> Debezium -> Kafka -> ClickHouse -> FastAPI
                                                  |
                                             Prometheus
```

PostgreSQL хранит исходные данные, Debezium доставляет изменения в Kafka,
ClickHouse считает показатели, API отдаёт их пользователю. Prometheus
помогает увидеть, что происходит с сервисом. Всё можно запустить на одном
ноутбуке в Docker Compose.

Redis, Grafana и отдельный обработчик потока добавляйте, если они помогают
вашей задаче. Кэш внутри процесса тоже ок. Другой стек можно обсудить, но
объясните, какую задачу решает замена и как вы проверите результат. Кластер
на несколько машин для проекта в целом не нужен и будет отвлекать.

Для магазина можно взять заказы, позиции заказов и платежи: три исходные
таблицы с понятными связями. Попробуйте добавить изменение состояния через
UPDATE. Например, заказ сначала создан, потом оплачен, затем отменён.
Дополнительно можно проверить удаление: что произойдёт с историей и
метриками, когда исходная запись исчезнет?

Для своей задачи выберите подходящую модель. Добавляйте таблицы, когда они
нужны для расчётов; подгонять их число под пример магазина не надо.

## Что должно получиться

- Стенд запускается из чистого клона по README, с пустыми томами.
- API возвращает хотя бы один показатель с описанным смыслом и контрольным
  примером, на котором можно проверить число.
- Изменение записи в исходной базе проходит через CDC и меняет результат
  в API без ручного переноса данных.
- В репозитории есть код, схемы, конфигурация и команды для повторения
  демонстрации. Оформление описано в разделе «Как оформить репозиторий».

Для основной демонстрации достаточно запустить стенд, получить исходный
результат через API, изменить запись в PostgreSQL и показать новый результат.
Сохраните команды и ожидаемые значения в README.

## Сначала пройдите весь путь

Начните с одного заказа и одной суммы. Создайте запись в PostgreSQL, найдите
изменение в Kafka, доведите его до ClickHouse и получите результат через
API. Измените заказ и убедитесь, что ответ тоже изменился. Сохраните это всё
как пример: он ещё пригодится при отладке.

Не зависайте сразу на идеальной схеме, миллионе событий или универсальном
обработчике. Сначала пусть весь пайплайн работает на десяти понятных
записях. Потом добавляйте остальные метрики, повторы, объём и поломки. Если
всё перестало сходиться, к маленькому примеру проще вернуться, чем искать
один потерявшийся заказ среди миллиона.

Для повторяемых экспериментов пригодится скрипт, который наполняет базу или
отправляет сообщения в Kafka. Можно взять [python-заготовку](generate.py),
адаптировать её под свою задачу или написать свою.

Запуск, параметры и форматы событий описаны в [справке генератора](GENERATOR.md).

Debezium envelope, события второй лабы и сообщения генератора имеют разные
форматы и требуют адаптации перед общей аналитикой. Во второй лабе удаление
логическое (`is_deleted=true`); физический DELETE и Kafka tombstone требуют
отдельной обработки.

Прямая отправка в Kafka подходит для отладки аналитики и нагрузки.
В итоговой демонстрации изменение записи в PostgreSQL должно доходить
до API через CDC.

## Идеи для развития

Когда весь путь заработал, выберите, что хочется попробовать дальше.

### Метрики с понятным смыслом

Можно развить проект до 3–5 бизнес-метрик и отдавать их через API.
Для каждого добавленного показателя опишите, что считается, по какой дате
отбираются данные, как учитываются изменения, удаления и возвраты.
Добавьте примеры, на которых можно проверить числа.

Для магазина можно взять несколько показателей:

- число и сумму актуальных оплаченных заказов;
- почасовую сумму по кампаниям с накопительным итогом;
- средний чек оплаченного заказа;
- сумму проведённых оплат и сумму возвратов за день.

Выберите подходящие своей задаче. Делать всё из списка не нужно.

<details>
<summary>Текущая сумма заказов и история оплат: почему числа разные</summary>

Сумма сейчас оплаченных заказов и сумма вчерашних оплат могут различаться.
Если заказ вчера оплатили, а сегодня отменили, текущая сумма уменьшится.
Но сама вчерашняя оплата от этого не исчезает. Для отчёта о движении денег
понадобятся платежи, возвраты или достаточная история изменений. Одного
последнего состояния заказа может не хватить.

</details>

### Корректность на изменениях

Попробуйте показать, что повторная доставка не увеличивает итог, старая
версия не заменяет новую, а отмена или удаление правильно меняет результат.
Выберите механизм, который соответствует вашему источнику и формату событий;
поле version из второй лабы само собой в Debezium не появится.

Для сверки можно подготовить контрольный SQL-запрос или небольшой скрипт.
Он должен независимо считать ожидаемый результат по исходным данным или сохранённой
истории. Сравните его с аналитикой после обработки контрольного датасета.
Если поток продолжает меняться, зафиксируйте, на каких именно данных делаете
сверку; два запроса в разное время могут закономерно получить разные суммы.

### Свежесть, которую вы измерили

Попробуйте выбрать допустимую задержку от изменения в исходной базе
до появления результата в API. Например, новая оплата должна быть видна не позднее чем
через 30 секунд при указанной вами нагрузке. Число выберите сами и проверьте
несколькими контрольными изменениями.

Запишите объём данных, скорость изменений, условия замера и результат.
Если используете кэш, его TTL тоже входит в задержку пользователя.
computed_at показывает время расчёта ответа, но свежий расчёт мог прочитать
данные остановившегося пайплайна. Одного этого поля для проверки свежести
недостаточно.

Для первого результата достаточно небольшого измеримого обещания. Если
ноутбук его не выдержал, покажите замер и объясните ограничение. Чужие цифры
из лекции в README переносить не надо.

### Поломка и восстановление

Можно проверить, что произойдёт с пайплайном при отказе одного компонента
и как вернуть его в строй. Выберите одну поломку, которую сможете повторить.

<details>
<summary>Пример: обработка остановилась, а новые данные продолжают приходить</summary>

Оставьте источник работающим, остановите один из этапов доставки или
обработки, внесите новые изменения, затем верните обработку.

Покажите, где заметно отставание, что видит пользователь API и как вы
понимаете причину. После восстановления дождитесь накопленных изменений
и сверьте итог. Перезапуск контейнера сам по себе ещё не показывает, что
данные восстановились правильно.

Сценарий с кэшем и недоступным ClickHouse из четвёртой лабы можно
использовать дополнительно. В опыте с остановкой обработки интересно
проверить, что изменения за время остановки в итоге дошли до аналитики.

</details>

## Как оформить репозиторий

Представьте, что ваш проект открывает человек, который не сидел рядом с вами
во время разработки. Из описания должно быть понятно, зачем это всё, как
запустить и куда смотреть. К тому же через месяц вы сами будете примерно
таким человеком.

### README с быстрым стартом

В начале README коротко опишите задачу и результат. Добавьте схему
пайплайна: Mermaid или обычная картинка подойдут.

Дальше нужен быстрый старт из чистого клона:

- что должно быть установлено и сколько ресурсов нужно стенду;
- какие настройки заполнить, с готовым .env.example;
- как поднять сервисы (условно `docker compose up -d --build`);
- как загрузить исходные данные и запустить поток изменений;
- где получить результат и посмотреть состояние сервисов, какой запрос сделать первым;
- какой ответ или результат должен получиться.

Постарайтесь, чтобы compose сам выполнял обычную инициализацию:
создавал таблицы и топики, регистрировал connector, дожидался готовности
зависимостей. Если после запуска нужны отдельные команды, дайте их в README
в правильном порядке. Не оставляйте шаги, которые существуют только в
истории вашего терминала.

Проверьте инструкцию на новом compose-проекте или другой машине. Должен
работать запуск с пустыми томами, а не только ваш уже прогретый стенд. Для
проверки не нужно удалять тома рабочего экземпляра. Зафиксируйте версии
зависимостей и Docker-образов.

### Данные, расчёты и примеры

Положите в репозиторий схему исходных данных, SQL аналитики, конфигурацию
CDC, код API и способ получить демонстрационный датасет. Опишите форматы
событий, ключи и порядок определения актуального состояния. Рядом с
метриками должны быть их определения и контрольные примеры.

Добавьте готовые запросы к API: получить показатель и увидеть результат
после изменения источника. Если есть фильтры по периоду или кампании,
покажите их в примерах. Не нужно заставлять читателя угадывать URL
и параметры по исходникам. Посмотрите
на оформление репозиториев проектов, которыми вы сами пользуетесь, и смело
стырьте оттуда пару идей по оформлению.

Пароли и токены в Git не кладите. Учебные локальные настройки отделите от
настоящих доступов; реальные рабочие данные для демонстрации не нужны.

### Дополнительные эксперименты и ограничения

Для своего стенда полезно записать короткий ранбук: как проверить состояние
компонентов, где смотреть логи и метрики. Если исследовали поломку, добавьте
команды для её повторения и восстановления, а также проверку накопленных
изменений. Если есть кэш, опишите поведение при отказе базы и предел
возраста выдаваемого ответа.

В дополнение к основной демонстрации покажите то, что исследовали:
сверку чисел, измерение свежести, поведение под нагрузкой или восстановление
после отказа.
Если эксперимент не удался, его тоже интересно обсудить: что ожидали,
что получили и где застряли.

В конце README перечислите ограничения: что пока не поддерживается,
какой объём вы проверили и что улучшили бы следующим шагом. Короткий
рабочий сценарий с понятными ограничениями вполне можно показывать и на
собеседовании. Запуск, который держится на вашей памяти и трёх открытых
терминалах с неизвестными командами, сначала стоит дописать.
